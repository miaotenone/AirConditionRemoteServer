# 设计：预配置 · 天气建议 · DHT11 反馈与夜间闭环 · 固件失联保护

日期：2026-10-15
状态：**定稿 v1（2026-10-15 已批准）**
关系：本文件是 [`AirConditionRemoteServer/docs/interface-spec.md`](../../Documents/VSCODEF/AirConditionRemoteServer/docs/interface-spec.md)
与 [`AirConditionRemoteCTL`](../../Documents/VSCODEF/AirConditionRemoteCTL) 固件设计的**增量**，不推翻其任何已定决策
（尤其：真值在 ESP32、控制决策在树莓派、所有动作最终走 `ac/cmd` 这一个出口、私聊单用户）。
涉及两个仓库：服务器 `AirConditionRemoteServer`（Python）+ 固件 `AirConditionRemoteCTL`（ESP32/PlatformIO）。

> 说明：这是**设计文档（What / Why）**，不是实施计划，也不含逐行实现。

## 1. 意图与缘由（Why）

现有系统已经能「卡片 / 说话 → `ac/cmd` → 空调」，且文本与卡片共用同一条动作管道。但缺三件东西：

1. **常用设置每次都要重新点一遍**：夏天/冬天的模式+温度+风速组合，每次靠手点或手打，重复且慢。
2. **人不知道今天该开多少度**：空调设定值和室外天气、体感脱节，没有外部信息帮你决策。
3. **发出去 ≠ 达到了**：现在卡片只能说「我发出了 `ac/cmd`」，「`⚠️ 未确认`」也只是「设备没回话」，
   跟「室温到底到没到」是两码事。人缺一个**物理结果**的反馈，系统缺一个**闭环**。

外加一条**安全诉求**：树莓派/网络没了之后，空调不该「失联还猛吹」——要能自己兜底关掉。

## 2. 范围

### 2.1 做

- **A 预配置（预设）**：可命名的一整套设置，支持增 / 删 / 改 / 套用；可挂一个固定时刻（定时）。
- **B 天气建议**：按 IP 定位 + 逐小时天气，每天定时推**建议卡**，一键执行。
- **C DHT11 反馈 + 夜间闭环**：读室温/湿度 → 存历史（5 分钟一条）→ 拉取式查询；
  夜间模式（手动开 + 时间段 + 设定值）下闭环调**设定温度/开关机**，风速锁低。
- **D 固件失联保护**：ESP32 检测 WiFi / MQTT / 服务心跳，任一持续失联 5 分钟 → 关空调；重连后恢复。

### 2.2 不做（本次）

- 不做多台空调、不做群聊 / 多用户（沿用单 owner、单前缀 `ac`）。
- ~~不做曲线图渲染（历史查询给**文字/表格汇总**，我的判断：先不做图形）。~~
  → **2026-10-15 改了**：历史查询除了那行文字，还给一张带折线的卡片（§18.11）。
- 不做云端中转；天气走公网 HTTPS 直连（树莓派出网）。
- 不接 LLM；文本解析仍是规则式。
- **不做**预设的「每日自动重复」——预设定时是**点一次、约一次**（见 §5）。

### 2.3 反目标（技术上跑通也算失败）

- **误触发**：随便说句话就把空调改了（沿用现有文本解析的防误触发立场，新增词同样从严）。
- **失控闭环**：夜间闭环为了零点几度反复开关机（抖动）、或把温度开到离谱。
- **失联误关**：网络抖一下就把空调关掉，或每次上电都误关。
- **刷屏**：新增卡片/回执把会话刷满。
- **数据谎言**：历史里存了根本没读到的温度。

## 3. 现状与约束

### 3.1 现状（已实现、不要碰坏）

- 服务器纯逻辑模块 `state.py` / `cards.py` / `actions.py` / `intent.py` / `replies.py` / `store.py` 与 I/O 分离，可离线单测。
- 动作管道唯一：`(action, value)` → 队列 → 去抖合并 `merge_actions` → 一条 `ac/cmd` → 乐观卡片 → `ac/state` 确认。
- 卡片是 **Card JSON 2.0**，单张遥控器卡原地 patch（`store` 记一个 message_id）。
- MQTT 契约：`ac/cmd`（发布）、`ac/state`（retained）、`ac/status`（retained + LWT）。
- 文本控制：私聊中文短句 → `Intent`，形容词句永不执行。

### 3.2 硬件约束（DHT11）

- DHT11：温度 **1℃ 分辨率、±2℃ 误差**；湿度 ±5% RH，量程约 20–90% RH。
- **采样率 ≤ 1 Hz**（建议 ≥ 1s 间隔，实际用 30s）。
- 读取**阻塞约 20ms**，且**无反馈**（读失败就是读失败）。
- 单总线：DATA 需上拉（裸 4 脚需 4.7k–10kΩ 拉 3.3V；3 脚模块多半自带）。

### 3.3 飞书卡片约束

- 表单容器 `form`、输入框 `input`、时间选择器 `picker_time`、日期时间选择器 `picker_datetime`
  **均属 JSON 2.0，需客户端 ≥ 7.20**；表单容器**必须放卡片根节点**，内嵌子项必须有唯一 `name`。
- 表单提交回调：`action.tag == "button"`、带 `action.form_value`（键＝各子项 `name`），
  另外带 `action.value`（按钮自定义回传）、`action.timezone`（如 `Asia/Shanghai`）。
- 自定义机器人菜单**在控制台写死**：菜单项显示名即发出文字。所以**动态预设只能体现在卡片上**，菜单只做固定入口。

## 4. 总览与数据流

```
                         ┌──────────── 新增/改动 ────────────┐
 飞书私聊                │  预设卡 / 设置卡 / 建议卡 / 反馈卡   │
  ├─ 菜单「其他 ▸ 预设」─┼→ 固定入口文字 → 动态预设卡（表单）   │
  ├─ 发一句话 ───────────┼→ 文本解析（历史查询 / 夜间 / 天气）  │
  └─ 点卡片 ─────────────┼→ 卡片回调（含表单 form_value）      │
                         └──────────────┬────────────────────┘
                                        │  统一动作管道 (a,v)
                                        ▼
                                 merge_actions → ac/cmd ─┐
                                                         │
  ┌─ 夜间闭环(服务器) ─┐   ┌─ 计划任务(scheduler) ─┐        │
  │ 读 ac/env + 天气  │   │ 预设定时 / 天气推送时间 │        │
  │ 纯函数决策 → 动作  │   │ 一次性到点触发          │        │
  └────────┬─────────┘   └──────────┬───────────┘        │
           └────────────► 同一个动作队列 ◄────────────────┘
                                        │
                                        ▼ MQTT
  ┌─────────── ESP32 固件 ───────────┐   ac/cmd   →
  │ DHT11 → ac/env (retained)         │   ac/hb    ← (服务心跳, 30s)
  │ 失联保护: WiFi/MQTT/hb → 5min → 关 │   ac/event → (fail-safe 汇报)
  │ 红外 → 美的空调                    │   ac/state (retained)
  └──────────────────────────────────┘   ac/status (retained + LWT)
```

新增的决策（夜间闭环、天气建议、预设套用）**全部产出 `(action, value)`**，进**同一个队列**，
因此去抖、乐观更新、确认超时、回执**全部继承**——与文本控制当初的做法一致。

## 5. A · 预配置（预设）

### 5.1 数据

一条预设 = `名字` + `{power, mode, temp, fan}` + `(可选) 固定时刻 HH:MM` + 「定时」开关。
**预设恒含全部四个字段**（相当于一条「多项命令组合」），套用时**整体下发——包含开关机**。
名字是**用户随便起的标签**（「夏天」「冬天」「睡觉」「客厅」），系统**不认识语义**。

### 5.2 交互

- **入口**：控制台菜单「其他 ▸ 预设」→ 点它发一句固定文字（如 `预设`）→ 机器人发一张**动态预设卡**。
- **预设卡**：列出已有预设（每条一个按钮）+ 「＋新建」。
- **新建 / 编辑**：换成**一张表单卡**（表单容器）：
  - 输入框：名字（必填）
  - 下拉：**电源（开机 / 关机）**
  - 下拉：模式（自动/制冷/除湿/送风/制热）
  - 下拉：风速（自动/低/中/高）
  - 下拉：温度（16–30）
  - 时间选择器：时刻（选填；填了即启用定时）
  - 提交按钮（`action_type: form_submit`）

  > 因「预设恒含全部字段」（§5.1），表单**必须**给出电源一项。
- **删除**：预设卡上每条带「删」按钮（二次确认）。

### 5.3 套用语义（已定）

- 没开定时 → **立即**套用（把 4 个动作入队，合并成一条 `ac/cmd`）。
- 开了定时 → **点的时候比时间**：
  - 今天该时刻**还没到** → 创建一个**一次性计划任务**，到点执行。
  - 今天该时刻**已经过了** → **立即**执行。
  - **不跨天**、**不重复**、**不自动触发**。
- 套用不产生额外确认；回执沿用现有 `✅ 已…` 风格，注明「已预约 22:30」或「已立即执行」。

### 5.4 与其它功能的关系

- 天气建议卡的「定时」**不做**——想定时就存成预设（已定）。
- 预设可成为夜间闭环之外的「白天一键场景」。

## 6. B · 天气建议

### 6.1 数据源（**我的判断**）

- **定位**：IP 定位拿经纬度（可用 `ip-api.com` / `ipinfo` 等免费接口）。
- **天气**：**Open-Meteo**（免费、无需 key、自带逐小时预报 + 体感/湿度）。
- 允许用环境变量覆盖经纬度（避免 IP 定位不准）。

### 6.2 触发

- 每天到**「推送时间」**自动推一张**建议卡**。
- 「推送时间」用**卡片表单**（时间选择器）设置，存本地库；设一次长期有效。
  （**我的判断**：不塞进 `.env`，因为你要在手机上随时改。）

### 6.3 建议卡内容

- 室外当前温度 / 体感 / 湿度；未来数小时走向（升/降、峰值时段）。
- **建议的空调设置**（模式 + 温度 + 风速），由**纯函数** `recommend(weather) -> (mode, temp, fan)` 产出。
- 按钮：`[立即执行]` `[忽略]`。执行 → 同一动作管道。

### 6.4 推荐规则（**我的判断**，纯函数、可单测、可调）

- 以室外温度带 → 建议目标温度带（如 ≥35℃→26、30–35→25、26–30→24、18–26→不推或送风、<18→制热）。
- 叠加**走向**修正：若两小时内明显降温，则建议偏高一度，避免过冷。
- 阈值全部集中在一个表里，方便你日后微调。
- **叠加室温校验**（Q2c，2026-10-23 真机验收后补）：有 DHT11 读数时，表值再和
  室温比一次——目标被室温**已经满足**（差 ≤1℃）→ 卡片写「不用开」，`[立即执行]` 不发命令；
  目标落在室温**错误的一侧**（如室外 16℃→制热 20℃，而室温 23℃）→ 改成室温±2 的
  可用值，而不是递一个「把房间加热得更冷」的建议。没有读数时行为与原来完全一致。

## 7. C · DHT11 反馈 + 夜间闭环

### 7.1 固件侧：读 + 报（不做决策）

- DHT11 每 **30s** 读一次（≤1 Hz 合规）；成功 → `ac/env` 发布 `{"temp":26,"humidity":55,"ok":true}`（retained）。
- 读失败 → 发布 `{"ok":false}`（**不带旧值**，避免服务器误用陈旧数据）。
- 具体接线/引脚见 §12。

### 7.2 服务器侧：记录 + 查询

- **记录**：每 **5 分钟**把最近一次 `ac/env` 落一条快照进本地库（`env_history`）。
- **查询**（拉取式，**发一句话**；也可挂菜单）：`当前` / `今夜` / `一天` / `一周` / `全部`。
  - `当前`：实时一条（室温、湿度、目标、差值、在线）。
  - `今夜`：本次夜间时间段内的聚合（最低/最高/平均、是否达标）。
  - `一天 / 一周 / 全部`：该窗口的聚合 + 极值，**并给一张折线卡片**（§18.11；最初写的是「只给文字」，用户 2026-10-15 要图）。
- **历史卡片**（`build_history_card`）：一行文字汇总 + 室温折线（夜间开着时叠一条目标线）+ 湿度折线 + `当前/今夜/一天/一周/全部` 五个按钮（点了**原地**重画那张卡）。
  - 发一句话查 → 文字回执 + 把卡发到**最下面**；点卡上的窗口按钮 → 原地 patch。
  - 窗口里**不到两个点不发卡**：一个点连不成线，文字「还没有记录」已经说完了。
- 复用文本路径（`intent.py` 加类目 + `replies.py` 出文案），零外部依赖可测。

### 7.3 夜间闭环

- **入口**：控制台菜单「其他 ▸ 夜间」→ 发固定文字 → 机器人发**夜间设置卡**；夜间开关、时间段、
  设定值**全部在卡片上设**（开关按钮 + 表单/时间选择器），长期存本地库。
- **进入**：**手动**开关（设置卡上的开关 / 文本「开夜间」「关夜间」）+ **配置时间段**（如 23:00–07:00）。
  - 手动决定「要不要进」；时间段决定「边界」：**只有落在时间段内闭环才按夜间规则跑**，
    到结束时间**自动退出**（就算你忘了关）。

> **总则（用户定）**：**凡是能配的东西，尽量做成卡片**——预设、推送时间、夜间段/设定值都在卡片上改；
> 菜单「其他」只挂**固定入口**（预设 / 夜间 / 天气 / 历史）。
- **目标**：**夜间设定值**（你在配置里设的目标室温）。
- **控制对象**：空调的**设定温度 / 开关机**；**风速永远锁低**（硬规则）。
- **输入**：DHT11 室温 + 趋势（最近若干条）+ 天气预报走向。
- **决策**（**我的判断**，纯函数 `decide(room, trend, forecast, target, ac, now) -> actions`）：
  - 室温高于 `目标+死区` → 确保开机 + 制冷/制热 + 设定温度朝目标压。
  - 室温低于 `目标-死区` → 抬设定温度；更极端 → 关机。
  - 达标带内 → 不动（可选：达标即关，见 §7.4）。
  - 趋势：环境本身在朝目标走（天气要变） → 少干预 / 不动作。
- **防抖（工程保护，**我的判断**）**：
  - 温度死区（如 ±1℃，兼顾 DHT11 只有 1℃ 分辨率）。
  - 最小动作间隔（如 ≥10 分钟）。
  - 设定温度永不越出 16–30。
  - 手动命令到达 → 闭环**临时让位**（如 30 分钟），避免和用户抢。
- **权限（已定）**：设定温度随便改、能自己开机、能自己关机、**风速只到低**。

### 7.4 待确认（见 §17）

- 「达标后是否自动关机」目前按「能关」实现（你已答「都可以」）。

## 8. D · 固件失联保护

### 8.1 判据（已定）

ESP32 维护 `last_contact`，以下**任一**成立即视为「断开」：

1. **WiFi 断**（`WiFi.status() != WL_CONNECTED`）。
2. **MQTT 断**（`connected()` 因 keepalive/PINGRESP 超时判失败）。
3. **服务心跳超时**：连续收不到 `ac/hb`（服务每 **30s** 发一条）。

> 为何要第 3 条：Mosquitto 与机器人服务是树莓派上**两个进程**，服务崩了 broker 还在，
> MQTT 的 PUBACK 只证明 broker 收到，证明不了「服务活着」。

### 8.2 动作（已定）

- 连续失联 **5 分钟** → **立刻发一帧「关机」红外**，并把 `g_state.power = 0`（重连后 retained 状态诚实）。
- **开机保护**：上电后必须**成功连上过一次**才启用本保护（否则每次重启误关）。
- 失联关机**只发一次**（不重复刷红外）。
- **重连后恢复**：ESP32 记住断联前状态，重连后发一条 `ac/event` 汇报 fail-safe，
  **由服务器决定并执行恢复**（决策统一在服务器），随后夜间逻辑照常继续。

### 8.3 可配置（**我的判断**）

- 阈值（5 分钟）、心跳周期（30s）先做成固件常量（`config.h`），可选开放到配网页/NVS。

## 9. 接口改动

### 9.1 MQTT 契约（两侧同步，含 `interface-spec.md` §4）

| Topic | 方向 | QoS | Retained | Payload | 新增? |
|---|---|---|---|---|---|
| `ac/cmd` | 服务→设备 | 1 | 否 | 变化字段 | 否 |
| `ac/state` | 设备→服务 | 1 | 是 | `{online,power,mode,temp,fan,brand}` | 否 |
| `ac/status` | 设备→服务 | 1 | 是 | `{online}` + LWT | 否 |
| `ac/env` | 设备→服务 | 1 | 是 | `{temp,humidity,ok}` | **新增** |
| `ac/hb` | 服务→设备 | 0 | **否** | `{online:true}` | **新增** |
| `ac/event` | 设备→服务 | 1 | 否 | `{type:"failsafe_off",prev:{…}}` | **新增** |

> `ac/hb` 与 `ac/event` **不 retained**：心跳/事件是「此刻发生」，retained 会制造假新鲜。

### 9.2 卡片（`cards.py` 新增，均 Card JSON 2.0）

- **预设卡**：列表按钮 + ＋新建 + 每条删除。
- **预设表单卡**：`form` + `input` + 两个 `select_static` + `picker_time` + 提交按钮。
- **设置卡**：推送时间、夜间时间段、夜间设定值（`form` + `picker_time`/`input`）。
- **建议卡**：天气摘要 + 建议设置 + `[立即执行][忽略]`。
- **反馈/历史卡**（可选）：历史查询结果也可用卡片呈现（**我的判断**：先文字回执，卡片留后）。

### 9.3 卡片回调归一化（改 `feishu_client.py` / `actions.py`）

- 现有：`action.value`（按钮）、`action.option`（下拉）。
- **新增**：`action.form_value`（表单提交，字典）——需透传给服务并映射成具体动作
  （如 `preset_save`、`settings_save`）。
- 路由：不同卡片用 `action.value.a` 前缀或卡片 `name` 区分，避免与遥控器卡的 `a` 冲突。

### 9.4 文本指令（改 `intent.py` / `replies.py`）

## 12. DHT11 硬件接线（重点）

**引脚（**我的判断**：选 GPIO4）**

| ESP32-WROOM-32E | DHT11 | 说明 |
|---|---|---|
| GPIO4 | DATA | 单总线数据；需 4.7k–10kΩ 上拉到 3V3（3 脚模块通常自带）|
| 3V3 | VCC | 供电（DHT11 支持 3.3–5V；用 3.3V 与 ESP32 电平一致）|
| GND | GND | 共地 |

**为什么是 GPIO4**：现有占用 21/22（OLED I2C）、16/17（红外 UART）。
GPIO4 空闲、可输出、**非 strapping 引脚**、**非仅输入脚**（34–39 不能用）。
引脚在 `pins.h` 定义（`#define PIN_DHT 4`），可换。

**注意事项**

- 裸 4 脚 DHT11 必须加上拉电阻；3 脚模块多半已带，先按模块来。
- 线长建议 ≤ 1m（DHT11 对时序敏感，长线易读失败）。
- 供电 3.3V；若读不稳再考虑 5V + 电平注意（不推荐，先 3.3V）。
- 采样 ≤ 1 Hz；固件用 30s。
- **OLED 可顺带加一行室温/湿度**（4 行布局有余量）——**我的判断**，可选。

**依赖（`platformio.ini`）**

```ini
lib_deps =
    …
    beegee-tokyo/DHTesp@^1.1.0     ; 非阻塞、ESP32 友好；备选 Adafruit DHT sensor library
```

**`docs/wiring.md` 同步**：把上表加进接线表。

## 13. 已知限制

1. **DHT11 精度差**（1℃ / ±2℃）：死区要开大；不要用它做 ±0.5℃ 级控制。
2. **闭环在服务器**：树莓派/网络挂掉时夜间闭环停摆；空调保持最后状态（**由 §8 fail-safe 兜底**）。
3. **卡片表单需客户端 ≥ 7.20**；低版本卡片内容会显示升级提示。
4. **时间用树莓派本地时区**；表单回传带时区（`+0800`），需做一次归一。
5. **IR 单向**：固件只能「发」关机帧，无法确认空调真的关了。
6. **菜单写死**：预设/设置都靠卡片承载，菜单只是固定入口。

## 14. 验收标准

1. 新建预设「夏天」（制冷 26 自动风，不开定时）→ 点它 → **一条** `ac/cmd` 含模式/温度/风速；卡片同步。
2. 预设「睡觉」挂 22:30 定时；22:00 点它 → 生成一次性任务，22:30 执行；23:00 点它 → **立即**执行。
3. 预设定时**不会**自己触发（无任何点击时，到点无命令）。
4. 到「推送时间」自动收到建议卡；点「立即执行」→ 一条 `ac/cmd`；点「忽略」→ 无命令。
5. 接上 DHT11：`ac/env` 每 30s 更新；历史每 5 分钟一条；发「当前」「一周」各回一条汇总。
6. 开夜间（时间段 23:00–07:00，目标 26）：室温 28 → 闭环调设定温度/开机，**风速=低**；室温 24 → 抬温度或关机；
   到 07:00 自动退出夜间。
7. **防抖**：达标带内不反复动作；两次动作间隔 ≥ 最小间隔。
8. **失联保护**：拔网线 / 停 Mosquitto / 停机器人服务，任一持续 5 分钟 → 空调关机、`ac/state.power=0`。
9. **开机保护**：上电后尚未连过——**不**触发失联关机。
10. **恢复**：失联关机后再联网 → 服务器把空调恢复到断联前状态，夜间逻辑继续。
11. 断网时 DHT 读失败 → `ok:false`，服务器**不**把旧值当新值记录。
12. 现有 **全部单测保持全绿**（纯逻辑扩展，不改既有断言）。

## 18. 构建者复核后的补充决议（2026-10-15，修订 §4–§14）

> 一次**只读**的「不知情构建者」复核提出了 6 个 blocker + 20 个 should-fix。以下是把其中
> **设计者能定的**全部定掉（标「**我的判断**」的仍可改）。**只有你能拍板的见 §19。**

### 18.1 卡片身份与消息模型（原 blocker B1/B7）

- `card` 表**按种类**存：`card(owner, kind, message_id)`；`kind ∈ {remote, preset, settings, weather}`。
  旧库自动迁移（旧的单行记为 `kind='remote'`）。
- 各类卡片**各占一条消息**，各自原地 patch：遥控器卡（remote）、预设卡（preset）、设置卡（settings）、
  建议卡（weather，每次推送**替换上一条**，不止干等着堆积）。
  - **例外（实测补，见 §18.10）**：**菜单入口**点出来的卡要**发到最新位置**——用户站在聊天底部，
    原地 patch 一张在屏幕上方好几屏的卡＝「什么都没发生」。按钮反馈仍就地 patch（手指正指着它）。
- **丢弃**「点谁就把指针指向谁」的旧行为：卡片回调**按动作词前缀路由**，不再改动 `remote` 指针。
- 卡片按钮的反馈：**就地 patch 那张卡**，加一行结果（`✅ 已预约 22:30` / `✅ 已保存` /
  `❌ 没有这个预设`）。触发 AC 动作时，遥控器卡照常同步。

### 18.2 动作词表与路由（原 blocker B3）

- **AC 动作**保持现有 6 个不变（`power/mode/temp/temp_step/fan/refresh`），只有它们进动作队列。
- **UI 动作**（同步处理、**绝不进 AC 队列**）：`preset_open` / `preset_new` / `preset_edit:<id>` /
  `preset_delete:<id>` / `preset_apply:<id>` / `settings_open` / `night_toggle` /
  `weather_exec` / `weather_ignore`，以及表单提交 `preset_save` / `settings_save`。
- 只有 `preset_apply`（展开成 4 个动作）与 `weather_exec` 会**入队**成 AC 动作。
- `actions.normalize_action` 增加这条「UI 动作」白名单，未识别一律忽略并记日志。

### 18.3 表单回调契约（原 blocker B4/S14）

- `feishu_client` 回调签名扩展为
  `(open_id, chat_id, message_id, value, option, form_value, card_name)`；`form_value` 原样透传字典。
- **表单元素 `name` 固定**：`name`(input) / `mode` / `fan` / `temp`(三个 select_static) / `at`(picker_time)。
  - 值编码：`mode`、`fan`、`temp` 用**整数码**；`at` 用 `picker_time` 回传的 `"HH:MM +0800"`。
  - **表单内的 select 走 `form_value`**（不再走 `action.option`）。
- **结构与现有 2.0 一致**：`form` 放在 `body.elements` **根层**；提交按钮
  `"tag":"button","action_type":"form_submit","name":"submit"`；`name` 输入框 `required:true`。
  （**实测修正见 §18.10**：2.0 起必须再带 `form_action_type:"submit"`。）
- 删除用按钮的 `confirm` 二次确认弹窗（2.0 支持）。

### 18.4 文本指令（原 blocker B6/S13）

- `Kind` 扩展为 `Literal["actions","query","help","unclear","suggest","history","night","weather","preset"]`；
  `replies.render` 补这些分支。
- **防误触发优先**：新类目一律**整句精确匹配**才认，且**排在 query/help/actions 之前**：
  - 历史：`当前` / `今夜` / `一天` / `一周` / `全部`（整句）。
  - 夜间：`开夜间` / `关夜间` / `夜间状态`（**不**认裸 `夜间`）。
  - 天气：`天气` / `今天天气` / `建议`（**不用** `今天开多少度`——它含 `多少度`，会被 query 吃掉）。
  - 预设入口：`预设` / `设置预设`（整句）。
- 预设套用走文本时**必须带动词**：`用<名字>` / `套用<名字>` → `preset_apply`，`hint=名字`；
  **解析器保持纯函数**（不查库），由服务解析名字；查不到回「没有这个预设」。纯名字（`夏天`）**不认**。

### 18.5 计划任务与时间（原 S1/S2/S3/S19/S20）

- **「推送时间」不是**一次性 `schedule`：它是 `settings.push_time`，由**每日 tick** 触发（每天一次）。
- **预设定时**才用一次性 `schedule`：点一次建一条，执行后置 `done`。
- **重启补跑**：`schedule` 的 `run_at` 若已过期**超过 15 分钟**→ 标记 `dropped`（**不**补跑，避免
  「22:30 的睡觉预设早上 9 点突然开机」）；未超过 15 分钟 → 立即执行。
- 时间：`run_at` 存 **epoch**；「今天 HH:MM」用**服务器本地时区**计算；表单回的 `+0800` 只做一次性归一，
  DST 由本地时间库处理。
- 夜间窗口**跨零点**：`start < end` 同日窗口；`start > end` 跨夜窗口；`start == end` 视为**非法**（表单拒绝）。
- 历史窗口：`当前`=最近一条；`今夜`=`settings.night_start~night_end` 的**最近一次**窗口（与是否曾开夜间无关）；
  `一天`=本地今日 00:00 起；`一周`=本地最近 7 天；`全部`=全表。

### 18.6 DHT11 数据可信（原 S4/S5/S7/S12）

- `ac/env` **retained**：服务器**忽略 retained 重放的旧消息**（paho 的 `message.retain` 标志）——
  **只在收到非 retained 的新消息时才记录/闭环**，杜绝「重启后把旧值当新值」。
- **读失败不落库**：`ok=false` 不进 `env_history`；聚合（极值/均值）**只算成功样本**。
- **闭环读到陈旧/失败数据 → 不动作**（`env` 超过 10 分钟或 `ok=false` 时停手）。
- **首次真接上 DHT11 就抓到一条假数据**（2026-10-15 晚）：第一条 `ac/env` 是
  `{"temp":0,"humidity":0,"ok":true}` —— **空模块的「全 0 帧」能通过 checksum**，于是带着
  `ok=true` 进来，被记成一条 0℃ 的历史（图会被这个点拽到谷底，正是 §3 那条「数据谎言」）。
  固件的合理性闸门本该拦住它：注释写着「比 DHT11 自己的 0..50℃/20..90% 略宽」，但代码写的是
  `humidity < 0.0f`，等于把 0% 也放行。**两端各补一道**：
  - 固件 `dht_read()`：湿度下限 **5%**（0% 是「没有读数」，不是干燥的房间）。待下次刷机生效。
  - 服务端 `parse_env()`：加 `TEMP_RANGE` / `HUMIDITY_RANGE` 闸门，越界一律 `ok=false` ——
    **服务端不假设固件把关**（旧固件、廉价传感器都会说谎；而且它才是写历史的那一方）。
    冷但真实的房间（3℃/45%）仍然收，有测试钉住，防过度收紧。
  - 那条 0℃ 的记录已从 Pi 的 `env_history` 删掉：**假数据比没有数据坏**。
- 定位/天气端点：用 **HTTPS** 服务（`ipwho.is` 或 `ipapi.co` + Open-Meteo），支持 `WEATHER_LAT/LON` 覆盖。
  （**实测修正见 §18.10**：`ipapi.co` 已返回 Cloudflare 挑战页，现按 `ipwho.is` → `ipinfo.io` 依次重试。）

### 18.7 夜间闭环细节（原 S6/S8/S9/S10/S11）

- **死区**：`±1℃`（兼顾 DHT11 的 1℃ 分辨率）。
- **设定温度写法**：室温 > 目标+1 → 设定温度=**目标**、确保开机、按当前/季节取制冷或制热；
  室温 < 目标−1 → 设定温度=**目标**、并倾向**关机**（见下）；带内 → 不动。
- **迟滞（防抖核心）**：**分开**关/开阈值——室温柔和到 `≤目标−1` 才关机；回升到 `≥目标+1` 才重开；
  再叠加**最小动作间隔 10 分钟**。杜绝整点反复开合。
- **趋势窗口**：最近 **6 条**样本（≈30 分钟）。
- **手动让位**：任何**用户发起的** AC 动作（遥控器卡/预设套用/天气执行/文本命令）记 `last_manual_at`，
  闭环让位 **30 分钟**；**闭环自己的** `ac/cmd` **不**计入，否则会永久自我让位。
- **夜间风扇**：夜间任何路径（含天气执行）产生的风速**一律夹到低**，闭环每个 tick 重新保证 `fan=low`。
- **天气 fetch 失败**：重试 1 次；仍失败则推一张「天气获取失败」卡（仅 `[忽略]`）。
  18–26℃ 建议**送风/通风**（仍出卡，`[立即执行][忽略]`）。

### 18.8 失联保护（原 B5/S16/S17/S18/S19）

- **`ac/event` 改为 retained + 带 `ts`**：解决「服务不在时事件丢失」；服务器**只在 `ts` 新鲜（<10 分钟）
  时**据其恢复，过期则忽略并清标志。
- **`ac/hb` 心跳**：服务器每 **30s** 发 `<prefix>/hb`（非 retained）；固件订阅 `<prefix>/hb`。
  两端都用**配置的前缀**，不写死 `ac`。

### 18.11 历史卡片改画折线（2026-10-15 晚，用户要求，推翻 §2.2/§7.2/P5）

**技术选型**：用飞书**原生图表组件**（`tag: "chart"`，基于 VChart），不是「服务端画 PNG 再上传」——
不需要图片上传权限（本应用也没开 `im:resource`），就是卡片 JSON，跟现有 2.0 卡同一套。

| 约束（实测/官方文档） | 值 |
|---|---|
| 客户端版本 | 图表组件需 **飞书 ≥ 7.1**；更低版本整块图变成「请升级客户端」占位 |
| 单卡大小 | **30 KB** 硬上限（更新卡片接口文档明写）；单卡建议最多 5 个图 |
| 实测量级 | 一天 288 个 5 分钟点 × 2 条线 = **22.5 KB**（太贴边）；一周 2016 点 = **77 KB**（直接超） |

留了三倍余量；这条有测试兜底（`test_a_history_card_stays_well_under_the_message_cap`）。

### 18.12 夜间首次真机实测：一个假警报 + 三个缺口（2026-10-15 夜）

当晚 `settings_save`（21:20，夜间 21:00–07:00 / 26℃）与 `preset_apply`（21:52「秋天-10」）都成功了，
但把下面这些**文档里还没有的**东西揪了出来。都是当晚实测，不是推断。

#### 1. 「⚠️ 未确认」是假警报 —— 命令**不需要改变任何状态**时也会报

日志里出现 5 次 `no ac/state came back in 5.0s; marking unconfirmed`，看着像设备没执行，**不是**：

| 环节 | 代码 | 行为 |
|---|---|---|
| 排队（乐观更新）| `main.py:342 / 529 / 923` | `pending = True` —— **排队时就置位了** |
| 真发出去 | `main.py:794-796` | 只有 `publish_command()` 成功才刷新 `_confirm_deadline` |
| 不需要改变 | `main.py:791-793` | `merge_actions()` 返回空 → `continue`：**不发 `ac/cmd`、也不刷新 deadline** |
| 过期判定 | `main.py:810-819` | `pending` 为真、deadline 却是旧的 ⇒ 下一 tick 立刻报「未确认」 |

⇒ 会被误报的两条路径都成立。当晚的铁证：`21:52:11.020` 那条警告**之前没有任何 `ac/cmd` 行**
（上一行是 `20:34:01`）—— 它只能是从一条**被合并成空**的排队动作里冒出来的。

**2026-10-16 更正（两处，都是真机实测）**：

1. **固件其实会立刻回。** `main.cpp:97` 的 `if (!changed) return;` 并不拦「值没变」：`changed` 是
   `ac_state_apply_field()` 的返回值，而它**对任何认得出的字段都恒为 true**（`ac_state.cpp`），
   所以 `changed` 的意思是「**认出了至少一个字段**」，不是「值真的变了」。实测（旧固件，no-op
   `{"fan":2}`）：命令发出后 **0.04s** 就回了 `ac/state`。⇒ 原先「固件不改变状态就不回」这一条**是错的**。
2. **真凶在服务端**：`pending` 在**排队时**就置位，而 `_confirm_deadline` 只在**真发出去**时才刷新 ⇒
   命令还没发出去时，下一个 tick 拿到的 deadline 要么是 `0.0`（开进程后的第一条命令），
   要么是**上一条命令留下的、已经过去的**时间 ⇒ 立刻报「未确认」。这解释了当晚 5 次里的多数。

**修法（已做，见 §18.13）**：服务端把 `pending` 与计时器分开（排队清零、发送时起跳），
合并成空的批次直接清 `pending`；固件顺手让「一个字段都不认识」的命令也回一次状态
（**防御性**，不是本缺陷的因 —— 服务端不会发未知字段）。

> ⚠️ 当晚我曾拿这条警告当「设备没执行」的判据去推断 ESP32 的行为。
> **它不能当判据**（假警报 + QoS0，见下 4）。要判断设备到没到，得看 `ac/state` 的实际内容。

#### 2. 重启就丢影子状态

状态只在内存（开机 `g_state = g_cfg.initial`，`main.cpp:205`）⇒ 刷固件 / 重启后网关自认「关机」，
而空调照旧 ⇒ **卡片会说谎**。当晚刷完固件就现过一次。

两个陷阱（都踩过）：

- 网关自认「关」时按**关机**：字段值没变 ⇒ `!changed` ⇒ **空操作**，什么都不会发生。
- 同一状态下按**温度**：会发一帧 `power=0` 的完整帧 ⇒ **真把空调关掉**。

**当下对齐办法**：发一条**会改变状态**的命令（如「开机」）。
**修法（已做，见 §18.13.2）**：网关把状态存 **NVS**，重启 / 刷固件后不再自认关机
（真机验证：改 25℃ → 重启 → 仍是 25℃）。「服务端收到 `ac/status {"online":true}` 时重推影子状态」
那条**没有采用**，理由见 §18.13.2。

#### 3. 天气每日推送：失败一次，当天就没了

`_maybe_push_weather()` 在**发送之前**就写 `S_WEATHER_PUSHED_AT`（`main.py:875`），随后 6 小时直接 return
⇒ 到点那次取数一旦失败，**当天不会再试**。当晚 17:00 实测：

```
17:00:00  pushing the daily weather suggestion
17:00:01  weather push skipped: no data
```

所以是一次**瞬时**失败，被「先标记后发送」放大成了「今天没有建议卡」。
**修法（已做，见 §18.13.3）**：**发送成功才标记** + 失败后按 `_WEATHER_RETRY_S = 300s` 退避重试，

- 对照：服务心跳 `ac/hb` 本来就是 QoS0。
- 要么把契约改成写实情，要么换一个支持 QoS1 的客户端库 —— **都还没动**。
  （真正在兜「状态不会太久不更新」的，是 retained + 固件每 30s 重发。）

### 18.13 三个缺口的修法（2026-10-16 凌晨）

#### 18.13.1 「⚠️ 未确认」假警报（§18.12.1）

#### 18.13.2 重启丢影子状态（§18.12.2）

- 只在**真的改了状态**时写一次（应用命令、失联关机）—— 30s 心跳不写，NVS 有写寿命；
- 开机 2 秒内按 `r` 的「恢复出厂」连它一起清掉。

真机验证：`{"temp":25}` → 重启 → `ac/state` 仍是 **25**（若退回初值会是 24）。
**判据是 `25` 而不是「没变」**：初值 `temp` 也是 24，只看「有没有变」是分不出来的。

**「服务端收到 `online:true` 就重推影子状态」没采用**：服务端的记忆就是从 `ac/state` 采纳来的，
网关重启时它**已经先采纳了网关的初值**（顺序：`status online:true` → 初值 `state`），
重推只会把初值再推回去；要真做，得再维护一份「我们最后命令成什么样」的状态 —— 又多一处在说谎的可能。
而 §18.12.2 那两个陷阱（关机会空操作、温度命令真把空调关掉）都是**状态错**引起的，NVS 治的正是这个根。

#### 18.13.3 天气推送不重试（§18.12.3）

`_maybe_push_weather()` 重写：到点（含服务晚于到点才起来）后**先试**，
`_push_weather()` 返回「卡真的发出去了」才写 `S_WEATHER_PUSHED_AT`；失败（取数空 / 还没有会话）
就按 `_WEATHER_RETRY_S = 300s` 退避重试，最多补到点后 `_WEATHER_CATCHUP_S = 2h`。
这一次推成功后，6 小时的去重照旧。

- `_DAILY_WINDOW_S`（60s）**删除**：唯一使用处就是这个函数，而「窗口内不成即放弃」正是缺陷本身。
- 副作用（可接受）：服务在到点后才起来（< 2h）也会补推一张「今天的建议」—— 比当天没有卡好。

### 18.14 服务端静默失联 4.8 天（2026-10-22 凌晨）

**现象**：01:08 报「连接丢失」，而这个说法来自**网关的 OLED**（设备自己的链路页）——
一直到我们查完才确认：设备那一侧同样认为「对端没了」，因为它已经 4.8 天没收到一条 `ac/hb`。

网关侧一切正常（`ac/state`、`ac/env` 每 30s 照发），
但线上 `ac/hb` **一条都没有** —— 塌的是服务端，而它自己一声不吭。

**时间线**（全部是日志原文，不是推断）：

| 时刻 | 证据 |
|---|---|
| 2026-10-17 06:31:12 | `journalctl -u ac-bot`：`Exception in thread paho-mqtt-client-ac-bot` … `json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)` —— paho 的网络线程**死了** |
| 2026-10-17 06:31:35 | mosquitto 日志：`Client ac-bot has exceeded timeout, disconnecting.`（23s 没有 PINGREQ = 那条线程已经不在了）|
| 之后 4.8 天 | mosquitto 里**再也没有** `New client connected … as ac-bot`；`ac/hb` 零条；`env_history` 不再增长；进程却还活着，systemd 看着一直 `active` |
| 2026-10-22 01:20 | 重启服务：`ac/hb` 30s 一条，恢复 |

**根因**：`ac/state` 的回调里跑着一次飞书 `patch_card`（`_on_mqtt_state` → `_render` → HTTPS）。
那一次飞书回了个非 JSON 的响应体，lark SDK 在**它自己的 unmarshal 里**抛了 `JSONDecodeError`，
异常从 `_on_message` 一路逃到 paho 的 `_thread_main`，线程退出 —— 而
`connect_async` + `loop_start()` 的自动重连**就跑在这条线程上**：线程没了，就没有下一次重拨。
此后 `publish()` 一律失败（日志里是 `could not publish …`），客户端成了哑巴 + 聋子。

三个因素**叠加**才酿成 4.8 天：

1. 异常能逃出回调（本次真因）。飞书侧的 `_on_card_action` / `_on_message` 早就用
   `except Exception: log.exception` 护住了自己，MQTT 侧漏了；
2. 一次飞书往返直接挂在 paho 的网络线程上 —— `_restore_after_failsafe` 的注释正是在防这件事，
   但 `_render` 没照做；
3. **没人盯链路本身**：设备侧有 5 分钟 failsafe，服务侧没有任何对应的看门逻辑，
   也没有一句话告诉业主。

**修法（服务端四层，每一层都能单独挡住下一次）**：

1. `app/mqtt_client.py`：新增 `_deliver()`，四个 payload 回调**全部**经它转发，异常只记日志；
   `_on_connect` 里的 `subscribe` 同样护住 —— 它也在同一条线程上；
2. `app/feishu_client.py`：新增 `_call()`，每次 OpenAPI 调用「**绝不抛**，抛了就重试一次」
   （规范 §10 早就写了重试一次，代码里一直没有）；`success() == False` 的普通拒绝**不重试**
   （重试多半也没用，还白花配额）；`send_card` 取 `data.message_id` 改成 `getattr` 兜底；
3. `app/main.py`：`_render_off_thread()` —— MQTT 回调里的卡片 patch 交出去（`_run_async`），
   paho 线程不再做飞书往返。`tick` 侧的 `_render()` 仍是同步的，行为不变；
4. `app/main.py` 看门（`_mqtt_step()`，每秒一次）：链路连续 `_MQTT_NOTICE_S = 120s` 不通
   （`connected == False` **或**心跳发不出去）⇒ 给业主发一条飞书提醒（同一次故障只发一次）
   + `MqttBridge.restart()`：换一个**全新**的 paho 客户端重拨，且 `loop_stop()` 放在后台线程里
   （join 一条卡住的线程会把 tick 一起拖死）；链路回来后补发一条「已恢复」。

**为什么不只做第 4 层**：看门只能看到「通不通」，而且在本次事故里它要等满 2 分钟才动手；
第 1、2 层才是把病根去掉 —— 回调里抛异常**不能再**是断链。第 4 层治的是「下次换个原因又静默死亡」。

**验证**：`pytest -q` → **400 passed**（新增 19 条；把第 1–4 层分别退回旧行为后，其中
**10 条变红** —— paho 回调抛异常、飞书 SDK 抛异常、卡片仍在 paho 线程上渲染、看门不动作）。
**既有断言一行未改。**

**顺带量到的事实**（说明当晚空调为什么是关着的，不是修坏的）：20:17 与 20:57 那两次
「开机 / 制热 26℃」都停在 `could not publish` —— 命令根本没发出去，设备从没收到过；
设备自己的认知一直是 `power=0`，所以失联 5 分钟触发的 failsafe 关机也是空动作。
这也解释了**用户看到的那个「连接丢失」**：网关 OLED 的链路页 4.8 天来一直在说
「对端没了」——它没有说错，是服务端真的没了。

> 修复后按用户要求补发了那一帧 `{"power":1,"mode":4,"temp":26,"fan":0}`：
> 设备 **0.2s** 内回 `ac/state = {power:1,mode:4,temp:26,fan:0}`，红外已发。
> （直发 `ac/cmd` 绕过了服务的「手动接管 30 分钟」记账，所以夜间闭环随即按设计
> 把风量压成低风 —— 它本身是认 `mode` 的：制热时太热才会真的关。）

### 18.15 外网断了、局域网还在，空调被误关（2026-10-23 白天，真机验收挖出）

观察到的链条（00:37–00:40 的日志）：飞书不可达 → `patch_card` 抛异常 → **`_render()`
只在 patch 成功后才写回快照** → 卡片内容每秒都「和上次成功的不一样」→ 1 Hz 的 tick
每秒重试一次，每次都是 30s 超时 ×2 次尝试。而 tick 线程**同时**欠设备心跳：设备
连续 5 分钟收不到心跳就按 §18.8 关机 → **外网断、家里网好好的，空调却被关掉**。

三档一起修（用户 2026-10-23 拍板「今天全部修」）：

1. **短超时**：`FeishuClient` 给 OpenAPI 客户端设 `timeout_s`（`FEISHU_TIMEOUT_S`，
   默认 **5s**；SDK 自己默认 30s）。一次调用最多 ~10s，不再是 ~60s。
2. **失败退避**：patch 失败后 `_RENDER_BACKOFF_S = 60s` 内不再重试同一内容；
   窗口一过或内容再变就再试 —— 卡片仍然是「最终一致」，但不会变成每秒一次的
   重试风暴。
3. **卡片 I/O 挪出 tick 线程**：新增 `renderer` 线程（`_request_render` 只举旗、
   `_renderer_worker` 干活），tick 只举手不干活；每日天气推送（取数 + 推卡）与
   预约执行回执同样走 `_run_async`。**tick 线程上不再有任何飞书/网络往返。**
   `_render()` 保持同步，因为点击/文本那条路上它就是「用户刚点过」的响应。

### 18.16 tick 线程不能死，业主的每条命令都算「手动」（2026-10-23 傍晚）

18.15 修完还剩两处同类的洞：**线程静默死亡**与**夜间闭环抢用户的设置**。

1. **tick 一趟异常不再带走线程**：`_tick_once()` 整趟包一层 try/except +
   `log.exception`。心跳就挂在这条线程上，18.14 的教训正是「线程死了没人知道」——
   网关 5 分钟收不到心跳就关机，而那看起来和「服务挂了」一模一样。现在一趟失败
   只丢这一趟，下一秒照常。
2. **预设 / 天气执行也让位**：`manual_until` 原来只挂在「文本指令」（`_on_text_message`）
   和「遥控器按钮」（`_on_card_action`）上，点预设、点天气「立即执行」、以及预约到点
   执行都不记 → 夜间闭环 10 分钟后就可能把你刚点的设置改回去。统一成一个
   `_yield_to_manual()`：**凡是带业主意图的命令**都让闭环退 30 分钟（18.7 的原意）。
   例外：「不用开」什么都没改，所以不让位。

**动机**：#8 一直只有「触发链」的证据（§18.14 那 4.8 天里设备确实进了 failsafe，但当时

1. **关机帧 = 当前值 + power=0**：`0x1D`=29℃、`04`=制热、`01`=低风都在，只有电源位翻 0 ——

2. **`ac/event` 非 retained 也安全**：服务当时不在场，这条事件本该丢（§18.8 一度要为此改成

   retained 重放与 `ts > 600s` 两道拦截 —— 防的是历史，不是这一次。
3. **恢复用的是事件里的 `prev`**，不是服务自己的影子：`prev.power==0` 时不做任何事（本来就关着，
   重发反而是惊吓），所以「服务停机期间用户用遥控器关机」不会被回滚。
