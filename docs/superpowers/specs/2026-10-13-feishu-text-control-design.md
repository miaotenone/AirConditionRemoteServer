# 飞书「对话控制」设计（文本指令 → 同一张卡片）

日期：2026-10-13
状态：**定稿 v1（已批准，2026-10-13）** —— 决策记录见 §10；构建者审查记录见 §11。
实现计划：`docs/superpowers/plans/2026-10-13-feishu-text-control.md`
上游：`docs/interface-spec.md`（定稿 v1，卡片按键侧）。本文件是它的**增量**，不推翻其任何决定。
本仓库当前状态：MQTT 已验证；服务骨架 + 78 项单测绿；卡片按键已实现；**文本只认召唤词 `设置卡片`（2026-10-14 起，旧词 `/ac` 等已退场，见 D22）**。

## 1. 意图与范围

### 1.1 要解决的问题

现在控制空调只有一条路：发召唤词（现为 `设置卡片`，原 `/ac`）→ 拿到卡片 → 点按钮。躺在床上时，**点按钮比说话麻烦**：
卡片的温度调节要点 `＋` 三下（或展开下拉），而人脑子里想的是「调低两度」。

所以要做的是：**让你可以直接对机器人说人话**，效果和点按钮一致，卡片同步更新。

> 一处**不**一致、且是有意的：卡片在关机时把 模式/温度/风速 置灰（`interface-spec.md` §5.3），
> 但文本路径**不置灰** —— 置灰是防手指误触，而打出来的字是明确意图，
> 「关着的时候先把温度设成 24，等下开机就是这个温度」是合理用法（固件整帧下发，温度位会被记住）。
> 此时回执**必须注明**（§5.4），不能说成「已设为 24℃」了事。

### 1.2 做

- 接收私聊文本消息，解析成**与按钮完全相同的动作序列** `(action, value)`。
- 覆盖：开关机、模式、绝对温度、相对温度（±）、风速、状态查询、帮助。
- 每条消息**最多产生一条 `ac/cmd`**（复用现有的去抖合并）。
- 执行后**回复一条短文本回执**（`✅ 已开机 · 制冷 · 24℃`），并原地更新卡片。
- 无法识别时给帮助文案，**绝不瞎猜着动空调**。

### 1.3 不做（本版）

- **不接大模型**。理由见 §6.1：空调是有副作用的物理动作，LLM 幻觉比不响应更糟；且需要 API key、联网、成本、延迟。规则解析能覆盖绝大多数真实说法。
- 不做多轮对话 / 上下文记忆（「再低一点」这种指代，v1 不认 → 回帮助文案）。
- 不做场景模板（睡觉/回家）、定时、温度曲线 —— 与 `interface-spec.md` §1「不做」一致。
- 不做群聊 / 多用户（沿用 `OWNER_OPEN_ID` 单用户）。
- 不解析图片、语音、富文本；`message_type != "text"` 在 `feishu_client` 处已挡掉。

### 1.4 反目标（技术上跑通也算失败）

- **误触发**：随便说句话就把空调动了（例如「今天好热啊」直接开机、或闲聊里的「3 度」被当成温度）。
- **动作与说法不符**：用户说「调低两度」，实际降了 1 度或 3 度。
- **刷屏**：一条消息发多条 `ac/cmd`（空调连响 + 红外满天飞）；或每条消息都新发一张卡片，把会话刷满。
- **重复执行**：同一条消息被飞书重投两次，「调低两度」变成降 4 度。

## 2. 核心架构决策：文本是「另一个输入适配器」

**这是本设计最重要的一条**：文本解析的产物与按钮点击的产物**在类型上完全一致**——都是 `(action, value)`，且 `action` 只能是 `ALLOWED_ACTIONS` 里已有的值。

```
文本消息 ──→ intent.parse(text) ──┐
                                  ├──→ [(a,v), ...] ──→ 同一个队列 ──→ merge_actions ──→ ac/cmd
卡片点击 ──→ actions.normalize ───┘                                     └──→ 乐观卡片 → 卡片同步
```

因此以下模块**一行都不用改**：

- `state.py`：`apply_action` / `merge_actions` / 夹取 / 指纹
- `main.py`：乐观更新、去抖窗口、确认超时（`⏳` / `⚠️ 未确认`）、卡片内容不变则不重发
- `cards.py`：卡片本身
- `mqtt_client.py`：完全不感知文本

好处：新特性带来的风险**只集中在一个纯函数模块**里，天然可单测（与现有 78 项同一套风格），且不会污染已经验证过的链路。

未来的 LLM 兜底（§6.2）也只是 `intent.py` 内部多一层，**不扩散到其它模块**。

## 3. 新增与改动的文件

### 3.1 新增（全部是纯函数，零外部依赖）

| 文件 | 职责 |
|---|---|
| `app/intent.py` | `parse(text) -> Intent`。文本 → 带标签的解析结果。**本设计的核心。** |
| `app/replies.py` | `Intent + AcState + Presence` → 回执文本。 |
| `tests/test_intent.py` | 意图解析单测（预计 50~70 项）|
| `tests/test_replies.py` | 回执文案单测 |

**解析结果的形状**（定死，`replies.py` 与将来的 LLM 兜底都按它对接）：

```python
Kind = Literal["actions", "query", "help", "unclear", "suggest"]

@dataclass(frozen=True)
class Intent:
    kind: Kind
    actions: tuple[tuple[str, int], ...] = ()   # 只有 kind=="actions" 时非空
    hint: str = ""                              # "hot" / "cold" / ""，供 suggest 选文案
```

| `kind` | 含义 | 行为 |
|---|---|---|
| `actions` | 解析出至少一个动作 | 入队 → `ac/cmd` → 回执 |
| `query` | `状态` / `现在多少度` | 只回状态文本 |
| `help` | `帮助` / `怎么用` | 只回帮助文本 |
| `unclear` | 没听懂（含**裸数字**歧义）| 只回「没听懂」+ 帮助 |
| `suggest` | 形容词句（§4.4），`hint` 带方向 | 只回引导文本，**不发 `ac/cmd`** |

为什么必须是带标签的结果、而不是光秃秃的动作列表：**「没有动作」有四种不同下场**，
回错文案是可见的错误（对说「有点冷」的人回「看着有点热？」）。

**否定说明**（§4.3）不单独占一个 `kind`：它落在动作里 —— `「不要制冷，开24度」` → `kind="actions"`，
`actions=[("temp",24)]`，`hint="negated:mode"`，回执里附一句「模式不动」。

## 4. 意图表面（grammar）

### 4.1 归一化（解析前统一做）

1. 全角 → 半角（`２４` → `24`、`℃` 保留语义）。
2. 去首尾空白与常见标点（`。` `！` `?` `~`）。
3. 中文数字 → 阿拉伯数字：`一~十`、`两`（`两度` → `2`）。
   **只在量词（度 / 档 / ℃）或温度动词（调到/升/降）附近的数字才转换**，避免「一直」被当成 `1`。
4. `COOL` / `HEAT` 等英文词小写化后同样识别。

### 4.2 动作表

| 意图 | 触发词（用户原话的例子）| 产出 |
|---|---|---|
| 关机 | 关、关掉、关闭、关机、停了、不用了、关一下 | `("power", 0)` |
| 开机 | 开、打开、开机、开一下、启动、开空调 | `("power", 1)` |
| 模式 | 制冷 / 冷风；除湿 / 抽湿；送风 / 吹风；制热 / 暖风 / 加热；自动 | `("mode", 0..4)` |
| 绝对温度 | 调到 24 度、设成 26℃、温度 24、24 度 | `("temp", 16..30)` |
| 相对温度 | 调低/降/低一点/凉一点 → `-1`；调高/升/高一点/暖一点 → `+1`；**低两度 / 升 3 度** → `±N` | `("temp_step", ±N)` |
| 风速 | 风速最大 / 大风 / 强风 → 3；中风 / 中档 → 2；小风 / 低风 / 弱风 → 1；自动风 → 0 | `("fan", 0..3)` |
| 查询 | 状态、现在多少度、开着吗、几度、怎么样了 | `kind="query"` |
| 帮助 | 帮助、怎么用、能做什么、指令 | `kind="help"` |

### 4.3 解析规则与歧义

- **一条消息可含多个动作**：`「开机制冷24度」` → `[("power",1), ("mode",1), ("temp",24)]`。
  下游 `merge_actions` 会把它们合并成**一条** `ac/cmd {"mode":1,"temp":24,"power":1}`。
- **数字必须绑定上下文**（关键的反误触发规则）：
  - `度` / `℃` → 温度
  - `档` / `档位` / `风速` / `风` → 风速
  - **温度动词白名单**：`调到 / 设成 / 设置成 / 设到 / 温度` → 后面的裸数字按温度处理。
  - **`开到 N` / `开成 N`** → **`[("power",1), ("temp",N)]`**。
    理由：「开到 26 度」的自然含义就是开机 + 26 度；只设温度会让人困惑（空调还是关的）。
    `开到` 里的「开」**不再额外**触发一次 `power`，它是同一个动作。
  - **其余裸数字**（`「2」`、`「这个 3」`、没有动词也没有量词）→ `kind="unclear"` + 反问，**不动作**。
- **优先级**：开关/模式词 → 温度 → 风速。同一字段出现多次时**后说的赢**（`「调到24，算了26」` → 26）。
- **否定**：紧邻否定（`不要 / 别 / 不用 / 不需要` + 动作词）→ 丢弃该动作，
  `hint` 里记 `negated:<field>`，回执附一句「模式不动」。不做句法分析，只认紧邻。
- **短词上锁**（实现后加严，见 §10 D15）：`开 / 关 / 停 / 打开 / 关闭 / 停了` 这些词在普通话里
  到处都是，所以它们**只有整句是对空调说的**才算命令 ——
  - 前面只能是称呼：空、`帮我`、`帮`、`请`、`麻烦`、`给我`、`空调`、`把空调`；
  - 后面只能是设备名（`空调`）或语气词（`了吧啊哦呀啦嘛哈着`）；
  - **或者**后面紧跟一个真动作：`开制冷24度`、`开2档`、`开到最大风`。

  这条是评审阶段抓出来的真 bug：`「没关系」` 会**关机**、`「开心」` / `「打开心扉」` 会**开机**、
  `「身高180」` 会**升温 180 度**。防误触发（§1.4）优先级高于覆盖率，宁可回「没听懂」。
  **代价**（故意接受）：`「一直开着」`、`「把窗户关了」`、`「雨停了」` 这类句子不动作。
- **相对变化必须有量词**：`低两度` / `冷3度` / `高一点` / `凉一点` 可以；`高140` / `热18` 不行。
  例外是 `调低` / `调高`：它们本身无歧义，单独出现就是 ±1（`降` / `升` 单独出现仍是 `unclear`）。
- **`档` / `档位` / `风速` / `风` 的绑定优先于温度动词**：`「调到2档」` 是风速 2，不是 2℃；
  `「开到2档」` 是开机 + 风速 2。
- **越界**：不在这里报错，交给已有的 `clamp_temp` / `clamp_mode` / `clamp_fan` 夹取；
  回执里**说明被夹了**（`✅ 已设为 30℃（温度范围 16~30）`）。
- **表情/噪声**：`「空调🥶」` → 只有「空调」，无动作 → `kind="unclear"` + 帮助。

### 4.4 形容词 / 情绪句：不执行，但要**分方向**（§10 D1）

`「太热了」`、`「有点冷」`、`「闷」` 这类句子里**没有可确定的动作**：
同样是「太热了」，有人想降 1 度、有人想降 3 度、有人想切成制冷、有人只是想开起来。

所以 v1 的立场是：语义上无法定死动作 + 无法定死幅度 → **不发 `ac/cmd`**，回一条引导，
`hint` 带方向，让文案对得上用户刚才说的话：

| `hint` | 触发词 | 回执 |
|---|---|---|
| `hot` | 太热、好热、有点热、热死、闷热 | `看着有点热？说「制冷 22 度」，或点卡片上的「制冷」。` |
| `cold` | 太冷、好冷、有点冷、冻死 | `有点冷？说「制热 26 度」，或点卡片上的「制热」。` |
| `""` | 闷、不舒服、有点难受 | `要调一下吗？说「制冷 22 度」或「风速最大」。` |

理由：让用户多说一句话的成本，远低于一次误触发（空调半夜突然全速制冷）。
这条立场**已定案**（§10 D13）：形容词句永不直接执行，永远不会走到 `ac/cmd`。
若哪天想改成「直接执行」或「带按钮的确认消息」，那是**新的一条特性**，要回到设计阶段。

## 5. 运行时行为

### 5.1 一条消息的完整时序

```
用户私聊发「调低两度」
  → 长连接消息回调（3s 预算内必须返回）
  → feishu_client 取 open_id / chat_id / message_id / text
  → main._on_text_message：
      1. _is_owner 检查（非 owner 静默忽略 + 记日志）
      2. store.mark_seen(message_id)——已处理过就丢
      3. intent.parse(text)
      4. kind=="actions" → 乐观更新 self.view + pending=True + 入队
         其它 kind     → 不回动作，直接构造回执
      5. 补卡（§5.2）→ 回执：reply_text(message_id, ...)
  → 去抖窗口（400ms）合并 → merge_actions(self.state, burst) → 一条 ac/cmd
  → ESP32 红外 → ac/state 回来 → 卡片去掉 ⏳（与按键路径完全相同）
```

**关键点：`_on_text_message` 与 `_on_card_action` 走的是同一个队列和同一个 `_publish_worker`**，
所以「3 秒内返回」的预算、去抖合并、确认超时全部自动继承，不需要新代码。

### 5.2 卡片不存在时：补一张（只补一次）

**规则：文本交互发生时若 `store.get_message_id(owner)` 为空 → 发一张新卡片并记住 `message_id`。**

适用于**所有** `kind`（包括 `query` / `help` / `unclear` / `suggest`），不只是执行了动作的那种。

> **例外（D22）**：召唤词 `设置卡片` 是唯一允许**无条件新发**卡片的路径 —— 它每次都发一张
> 新卡、把指针切到新卡、再撤回旧卡（撤回失败则把旧卡降级成一行提示卡，见 §10 D22）。
> 其余任何路径（含普通命令的补卡）都仍是「只补一次、之后只 patch」。

- 为什么包括无动作的消息：形容词引导里写着「点卡片上的…」，没卡片就成了死路；
  统一成「第一次跟机器人说话，就地给你一张遥控器」，规则简单且引导文案永远成立。
- 为什么不构成刷屏（§1.4）：`message_id` 记住之后**永远只 patch 不新发**，
  所以整个生命周期里最多只多出**一张**卡片。

### 5.3 去重

同一 `message_id` 只处理一次（`store.mark_seen`）。

**为什么必须做**：飞书事件可能重投，而**相对动作是非幂等的**——「调低两度」执行两次就是降 4 度。
绝对动作（`power`/`temp`/`mode`/`fan`）重复执行无害，但统一走一套去重，逻辑更简单。

**去重只挡「同一条消息的重投」，不挡「用户发了三次」。** 用户手打三次「调低两度」＝三条独立指令，
按序累积（见 §8 验收 #11）。

### 5.4 回执文案（统一格式，短）

| 场景 | 文案 |
|---|---|
| 执行成功 | `✅ 已开机 · 制冷 · 24℃` |
| 关机时设了温度/模式/风速 | `✅ 已设为 24℃（当前关机，开机后生效）` |
| 发生夹取 | `✅ 已设为 30℃（温度范围 16~30）` |
| 有否定被忽略 | `✅ 已设为 24℃（模式没动）` |
| 查询 | `现在 开机 · 制冷 · 24℃ · 自动风 · 🟢 在线（更新于 12:03:41）` |
| 帮助 | `能听懂这些：开机 / 关掉 / 调到24度 / 制冷 / 风速最大 / 状态` |
| 没听懂 / 裸数字 | `没听懂这句。试试：开机 / 关掉 / 调到24度 / 制冷 / 风速最大 / 状态` |
| 形容词 | 见 §4.4 的三条 |
| 设备离线 | `✅ 已发出（设备离线，可能不生效）` —— 由 `presence.online` 决定 |
| 非 owner | **不回**（避免探测，与 `interface-spec.md` §10 一致）|

回执反映的是**设备真实状态**（最后一个 `ac/state` + 本次乐观动作），不是「我发了什么」。
多条动作混在一句里时（§4.3 的组合），回执合并成一行，**不拆成多条消息**。

> **落地定稿（2026-10-13，实现后回填）**：所有「执行类」回执统一成
> **`✅ 已` + 完整状态行 +（修饰）**，例如
> `✅ 已开机 · 制冷 · 24℃ · 自动风（当前关机，开机后生效）`。
> 上表里的 `✅ 已设为 24℃`、`✅ 已发出` 是这一种的简写 —— 实测中省掉状态行会让人不知道
> 「设成了什么」，也和「执行成功」那行不一致。修饰语仍是表中的四种，多条用 `；` 连接，
> 顺序固定 **夹取 → 否定 → 关机 → 离线**。`没听懂` 行按原样实现（`试试：`，与帮助行的
> `能听懂这些：` 不同前缀）。最终文案以 [`../plans/2026-10-13-feishu-text-control.md`](../plans/2026-10-13-feishu-text-control.md)
> 的测试为准，接口侧摘要见 [`interface-spec.md` §5.6](../../interface-spec.md)。

## 6. 边界：为什么不接大模型，以及将来怎么接

### 6.1 为什么 v1 不接

1. **副作用**：发错 `ac/cmd` 会真的动空调。LLM 幻觉在聊天里是「说错话」，在这里是「半夜开机」。
2. **成本与依赖**：需要 API key、外网、按量计费，并给一个已经「零外部依赖可测」的仓库引入不可测的组件。
3. **覆盖率**：空调指令的语言空间极小（开关 + 4 个枚举 + 一个 16~30 的整数），规则解析足够。
4. **可测性**：规则解析是纯函数，50~70 项单测毫秒级跑完；LLM 只能做集成测试。

### 6.2 将来怎么接（预留，不在本版）

- **接口形状不变**：仍然是 `parse(text) -> Intent`（§3.1）。
  LLM 兜底在规则返回 `kind == "unclear"` 时被调用，**必须产出同样的 `Intent`** ——
  包括允许它回 `unclear` / `suggest`，而不是硬凑一个动作。
- **白名单过滤**：LLM 给出的 `action` 必须在 `ALLOWED_ACTIONS` 内，值必须能被 `clamp_*` 夹取，否则整体丢弃。
- **低置信一律降级为 `suggest`**（回引导让用户点卡片），不直接执行。
- 需要新增配置（API key / 模型 / 超时）与一条降级路径（LLM 不可用 → `unclear`），这两件事都要单独写 spec。

`tests/test_intent.py`（纯函数，无飞书/无 MQTT/无 broker）：

## 10. 决策记录

### 已定（定稿，2026-10-13 批准）

1. **文本与按钮共用动作管道**（§2）。这是本设计的骨架，换掉它等于重写。
2. **不接大模型**（§6.1）。规则解析 + 白名单预留。
3. **数字必须绑定动词或量词**（§4.3），其余裸数字一律 `unclear` + 反问。宁可多问一句，不可猜错。
4. **`开到 N` = 开机 + 温度 N**（§4.3）。这是唯一一处「一个词触发两个动作」的例外。
5. **文本路径不继承卡片的关机置灰**（§1.1），但回执必须注明关机状态。
6. **回执用「回复消息」**（`reply_text`），不新开消息；卡片原地 patch。
7. **去重落 SQLite**（`store.seen`），与现有 `store` 风格一致、可单测、重启后仍有效。
8. **去重只管重投，不管重复发送**（§5.3）；连发三次＝三条指令（§8 #11）。
9. **无动作的消息也补卡，但只补一次**（§5.2）。
10. **解析结果带标签**（`Intent`），`replies.py` 只负责文案、不做分类（§3.1）。
11. **设计文档放 `docs/superpowers/specs/`**：与姊妹仓库 `AirConditionRemoteCTL` 的既有约定一致。
12. **形容词句永不直接执行**（§4.4）：`「太热了」` 只回引导，**不发 `ac/cmd`**。
    否掉了「开机+制冷+降1度」与「带按钮的确认消息」两个备选。
    想改的话是**新特性**，要回到设计阶段 —— 这条是本版范围的分界线。
13. **相对温度别名偏保守**：`「凉快一点」` 按 `−1`（不是 `−2`）。
14. **模糊说法一律 `unclear`**：`「智能一点」` 这类不做映射，回帮助文案。

### 实现后补定（2026-10-13，代码评审逼出来的）

15. **短词上锁**（§4.3）：`开 / 关 / 停 / 打开 / 关闭 / 停了` 只在「整句是对空调说的」时才算命令。
    这是评审抓到的**真 bug**（`「没关系」` → 关机），修法选择了**加严解析**而不是加白名单/加确认，
    因为防误触发是本设计的第一优先级，且加严的代价只是「少数句子回没听懂」。
16. **`档` / `档位` / `风速` / `风` 绑定优先于温度动词**（§4.3）：`「调到2档」` = 风速 2。
    原设计只写了「数字必须绑定上下文」，没说两者同时出现时谁赢 —— 按「更具体者胜」定死。
17. **回执统一成 `✅ 已` + 完整状态行 +（修饰）**（§5.4）：设计表里的 `✅ 已设为 24℃` /
    `✅ 已发出` 是简写，实现时统一了；修饰语种类与顺序（夹取 → 否定 → 关机 → 离线）不变。
18. **`没听懂` 用 `试试：`，帮助用 `能听懂这些：`**（§5.4）：对没听懂的人说「能听懂这些」像在教训人。

### 联调后补定（2026-10-14，真机验收逼出来的）

19. **底部常驻控制用「机器人自定义菜单」，不用代码**：菜单项的响应动作选**发送文字消息**，
    点菜单＝发一条文本，直接复用已验收的文本路径（解析、去抖、回执、补卡全一致）。
    否掉了「推送事件 `application.bot.menu_v6`」（要新增事件分支与去重，纯重复）和
    OpenAPI 改菜单（`im/v1/chats/:chat_id/menu_tree` 是**群菜单**，与机器人菜单无关）。
    配置在控制台、需创建版本发布；线上用**悬浮菜单**（5 组容器 × 14 子项，见 D23）；
    「发送文字消息」动作需客户端 **≥ 7.22**（低版本菜单项不显示）。
    步骤与菜单表见 [`docs/feishu-setup.md`](../../feishu-setup.md) §13。
20. **回执传「动作前」的视图**（`main.py`）：`render` 自己会把动作再套一遍算「将要变成什么」，
    所以必须喂给它应用**之前**的状态。否则相对动作被算两遍 —— 真机上出现过
    `ac/cmd {"temp":28}` 配一条说 `26℃` 的回执（30 → 28 → 26）。验收 #11 因此要求 22/20/18。
21. **卡片点击解不出字段时，把原始报文打进 WARNING**，并支持扁平字段与字典两种形状
    （`_pick` / `_get`）。2026-10-14 真机丢过点击：报文不符合已知形状时，
    处理器静默退化成 `operator="" / value=None`，服务侧看成非 owner 直接丢弃 ——
    日志里**毫无线索**。现在解不出来会留下报文，下一次一眼定位。

### 召唤词改版（2026-10-14，用户反馈「召唤不到最新位置」后定案）

22. **唯一召唤词 `设置卡片`；召唤 = 新发 → 换指针 → 撤回旧卡**：
    - 旧召唤词 `/ac`、`/start`、`ac`、`空调` **全部退场** —— 它们落到解析器判 `unclear`，
      回「没听懂这句。…」并照旧补卡（§5.2 / §8 #8）。
    - 召唤语义：**发新卡 → `store` 指针切到新卡 → 撤回旧卡**。顺序不可反：
      新发失败就不撤旧的，旧卡继续可用。
    - 撤回失败（飞书默认 24h 撤回时限）→ 旧卡 patch 成一行提示卡
      （`遥控器已更新，最新一张在下面 👇`）；patch 也失败 → `log.warning` 后放弃
      （旧卡点了也没事：`_on_card_action` 会把指针切回被点的那张，自愈）。
    - 召唤词**不发文字回执** —— 卡片出现在最新位置本身就是反馈。
    - 匹配容错：比较前 `.strip()` 并去掉尾部 `。！？!?.`（`设置卡片。` 也能召唤）；
      只影响召唤词判断，不改动传给 `parse()` 的原文。
    - **普通命令路径一律不动**（§5.2 的「只补一次」、`_render` 原地 patch、去抖队列、
      回执渲染保持现状）—— 否则每发句话卡片都乱跳，违反反目标 1.4。

### 菜单改版（2026-10-14，用户拍板「分组式」）

23. **菜单 = 5 个分组容器 × 14 子项**（主菜单由用户指定 `卡片 / 模式 / 风速 / 开关 / 其他`，
    子项由实现方定。**温度刻意不上菜单** —— 调温走卡片或手打 `降2度`/`调到26度`）：
    - 结构：`卡片 ▸ 设置卡片 / 状态`、`模式 ▸ 自动 / 制冷 / 除湿 / 送风 / 制热`、
      `风速 ▸ 自动风 / 低风 / 中风 / 最大风`、`开关 ▸ 开机 / 关机`、`其他 ▸ 帮助`。
    - 已知取舍：**所有动作都是 2 拍**（先点组、再点项），包括最高频的开关机；换来的是菜单
      一眼能看懂。嫌开关机慢就把 `开关 ▸` 拆成两个一级项 —— **改菜单不用动代码**。
    - **主菜单项带子菜单时没有响应动作（纯容器）**：控制台里点 `+ 新建子菜单` 会弹
      「**新建并转移**」，把主项的**名称 + 响应动作**整体搬进新的子项，主项只剩一个空名称。
      所以建组顺序必须是「**给主项起名 → 新建子菜单 → 再把主项名称补回来**」。
    - **新建的子项默认动作是「跳转至指定链接」**，每一项都要手动改回「发送文字消息」。
    - 菜单项**没有独立的消息内容字段**：**显示名就是发出去的文字** —— 显示名必须写成
      解析器认识的整词（`中风` / `最大风`，不能只写 `中` / `高`）。
    - `风速高` 依旧**不可用**（`_FAN_LEVELS` 里没有「高」，解析成 `unclear`）。

## 13. 已知限制（实现 + 评审后回填，2026-10-13）

这一节记录**本版刻意不修**的东西。它们都来自一次独立代码评审，都是真的，但修它们要么越出本特性
的范围，要么代价大于收益。**联调时按这里的口径判断「是不是 bug」。**

1. **相对命令的基准是最后一次真值，不是乐观视图。**
   `_publish_worker` 用 `merge_actions(self.state, burst)` 合并 —— `self.state` 只由 `ac/state` 更新。
   于是：连发三条「调低两度」**快于** `ac/state` 往返 → 合并成一条 `{"temp":22}`（§8 #11 的预期）；
   **慢于**往返（用户打字本来就慢）→ 三条各自从当时的真值算，若真值还没刷新，三条都会算出 22，
   设备只降 2 度，而回执（乐观视图）说降了 6 度。
   这是**既有管道**的性质（卡片连点也一样，`merge_actions` 一直是这个基准），不是文本控制引入的。
   要改得把基准换成 `self.view`，那会动到已经验证过的卡片路径 —— 属于**新特性**，本版不动。
   **联调口径**：§8 #11 按「连发」测。
2. **回执在长连接回调线程里同步发 HTTP。** 最坏 3 次串行调用（补卡 + patch 卡片 + 回复），
   常态 1 次（卡片已存在就不补、内容没变就不 patch）。3 秒预算够，但会占住事件循环。
   与卡片路径同一风格（它也是同步 1 次），本版不动。
3. **标点与表情被当噪声丢掉**：`「调到24。5度」` → `「调到245度」`。空调指令这个语域可接受。
4. **`seen` 表只增不删**：每条文本一行，一年量级可忽略；要清就删掉 `ac-bot.sqlite3`。
5. **`stop()` 不关长连接**（`FeishuClient` 没有 `stop`，既有行为）。文本路径给回调加了一个
   `store` 调用者，所以 `stop()` 之后若还有消息进来会撞上已关闭的 SQLite —— 只在进程退出时发生。
6. **多字动词仍按子串匹配**：`「打开窗户」` 会开机（`打开` 是 §4.2 列的词）。短词已经上锁（§4.3），
   多字词保持子串匹配是**刻意的**：否则 `「帮我开一下」` 这类正常说法会被拒。
7. **`降` / `升` 单独出现不动作**（§4.2 原本写 `降` → −1）。它们太短、太容易出现在别的句子里
   （`「血压降了」`），改成必须带量词：`降两度` / `降一点`。`调低` / `调高` 不受影响。
8. **底部菜单不归代码管**（§10 D19 / D23）：机器人自定义菜单在**控制台**配置并**创建版本发布**
   才生效（约 5 分钟）；线上是**悬浮菜单**（5 组容器 × 14 子项，主菜单项本身无响应动作）；「发送文字消息」动作需
   客户端 **≥ 7.22**，低版本菜单项**不显示** —— 看起来像「配了没生效」，服务侧其实完全正常
   （判据：点一次日志里有没有 `text message from …`）。菜单文字改动不需要动服务，
   步骤与菜单表见 [`docs/feishu-setup.md`](../../feishu-setup.md) §13。
